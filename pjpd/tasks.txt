Settle the criteria-verification standard across the ontology_spec doc sets, then update the skill at /home/roby/.claude/skills/ontology_spec to match.

Two existing projects implement the criteria/test binding differently:

- /work/hggames/survive — CRITERIA.md R-rows have no status column. test/smoke.js holds all rule assertions as check('R-n ...', cond), and a coverage assertion greps CRITERIA.md for R-\d+ and fails if any ID lacks a check() labelled with it. Also has tools/tune.js (self-play with constant overrides, prints X-* proxies) and test/browser.js (headless Chromium, screenshot per screen) backing the U and X rows.
- /work/yuwakisaweb/ideas/hexandcounter — CRITERIA.md adds an Instrument column with exactly four values (automated / manual - <what a human checks> / not yet covered / retired), one test/R-n/ directory per automated criterion, and test/coverage.js checking both directions, run by node test/run.js.

Decision to adopt:

1. Keep the Instrument column with its four values. Its point is that "not yet covered" is a legal, visible state. Survive's format cannot express a known gap: an uncovered rule must either be deleted from the table or given a hollow assertion to satisfy the grep.

2. Drop the test/R-n/ directory requirement. It does not actually enforce "one rule per test" (nothing stops a file in test/R-7/ asserting three things) and it forces a parallel taxonomy plus a custom runner onto projects that already organize tests another way. Bind a test to its criterion by putting the ID in the test name instead, using whatever the project's framework already provides (Jest describe('R-9 ...'), a check() label, etc.).

3. Make the coverage check bidirectional: every row whose Instrument is "automated" must have at least one test labelled with its ID, AND every ID found in a test label must correspond to a row that is marked "automated". Survive only checks the first direction, which leaves orphan tests for deleted criteria.

4. Read criterion IDs from the table's ID column only, never by grepping the whole document. Survive's whole-file regex turns any prose mention ("superseded by R-21c") into a phantom requirement and makes a criterion impossible to retire without scrubbing every reference to it. This is also why the "retired" tombstone value is needed.

5. Adopt survive's RATIONALE Evidence line as a required field on any tuned decision: the line names the command that produced the number, e.g. `GAMES=40 ROUNDS=120 SEED=900 node tools/tune.js` followed by the result. This is the discipline that caught survive's own wrong prediction - the duel table predicted 8-13 dice was right, self-play showed survivors going down in a median of 2 shots, and D-5 records both the first decision and the correction. A modelled number is never stated as fact.

Skill edits required: the skill's "Tests: the directory is the label" section currently mandates test/R-n/ directories and describes them as the only link between a criterion and its tests. Rewrite it around ID-labelled tests, keep the coverage test but specify both directions and the ID-column-only scan, and keep the four Instrument forms unchanged. Add the Evidence-line requirement to the RATIONALE section. Cite /work/hggames/survive as the worked example throughout; it is the fuller reference, with hexandcounter noted as the source of the Instrument column.

Follow-on for /work/oblique once the skill is settled: CONSTRAINTS.md already uses the Instrument column and lists seven not-yet-covered rules (R-6, R-13, R-15, R-16, R-19, R-20, R-21), so only the coverage check needs writing, against the existing Jest suite organized by source file - no directory reorganization. Separately, none of the 23 tunables in ONTOLOGY section 6 currently has an Evidence line, which needs a committed harness before it can be fixed.

Reference capture, not a unit of work: Claude's stated preferences for the ontology_spec doc format, recorded 2026-10-17 after writing a full set for /work/oblique and reading the two mature examples (/work/hggames/survive and /work/yuwakisaweb/ideas/hexandcounter). These are opinions, not designer decisions - treat every one as [P]. The test-binding and Evidence-line preferences are deliberately omitted here because they are already captured as a decision to adopt in a separate ticket.

WHAT EARNS ITS KEEP

1. The explicit priority ordering in section 0 is the highest-value line in the whole set. Most specs list goals; almost none rank them, and the ranking is the only thing that turns a wish list into a tiebreaker. Oblique's "G-2 > G-1 > G-3 > G-5 > G-4" (restraint beats wit) settles arguments that the goal text alone leaves open. A goals list submitted without an ordering should be treated as incomplete.

2. Serves: tags are the best pruning tool in the format, and the check should run in both directions. "An item that serves nothing is a candidate for cutting" is the direction everyone does. "A goal that nothing serves is unmet" is the direction everyone skips, and it is the one that finds missing features rather than dead ones. This is mechanizable: parse the Serves: lines, diff the cited goal IDs against the section 0 list, report both orphan sets.

3. The pseudocode length limit is a detector, not a style rule. "If a rule cannot be written in under ten lines it is too vague to implement" is what makes the exercise worth doing. Forcing oblique's rules into pseudocode is what surfaced the createReplyTask spread-order bug and the unreferenced ID generators - neither was visible while reading the code as code.

4. Write the commands/events interface before the engine, whatever position it occupies on the page. Survive's own docs/PROCESS_REVIEW.md admits section 7 was added after the first build, where it had been invented during implementation instead. That is the strongest evidence in either repo for the rule, and it comes from the project that violated it.

5. "Code wins" on conversion, with the discrepancy list as an explicit deliverable. Oblique's conversion turned up 13 places where the old spec and the code disagreed; all 13 went into the log, none were silently fixed in either direction. The pull toward fixing while documenting is strong and it produces one unreviewable change.

6. A dead-vocabulary section (oblique's section 1.10). Names that still exist in code but no longer mean anything need somewhere to go that is neither "current state" nor "silently deleted". Not currently in the skill; it should be.

7. Batched open questions, each carrying a recommendation. The recommendation is what makes a Q answerable in one pass - a bare question gets deferred. Corollary worth stating: not every Q needs a ticket. A Q that is a designer decision rather than a repair should stay ticketless (oblique's Q-6, prompt injection having no mechanical prevention, is the example).

WHAT I WOULD CHANGE

8. Generating the Numbers table from code should be mandatory, not "ideally". A hand-maintained table of constant values is the most drift-prone artifact in the set, because it is the one thing that is both duplicated and frequently edited. Oblique has 23 hand-copied tunables and they will drift.

9. Ban section-number citations outright, including inside the doc set. The skill already says to prefer stable IDs, but survive's CRITERIA still carries group headers like "Damage (section 4.1, 4.2)" - exactly the references that break on reorganization. Name the rule instead.

10. An entity's field table must carry Notes that the type declaration cannot - ranges, invariants, who writes the field, when it is valid. If a table is just the TypeScript types transcribed into Markdown, it is worse than nothing: it will drift and nobody will read it. The goal is "every piece of state has a named home", not a schema dump.

11. Fewer documents for a single-author project. Survive's own retrospective scores TELOS as low-use (hence folded into section 0) and DYNAMICS as mostly dormant after design. Oblique folded RATIONALE into ARCHITECTURE_LOG, which was right there: with one author and a short history, the Why and the When are the same story. Split them once there are multiple maintainers and the Why needs to be readable without scrolling through dates.

12. The format should require a short retrospective after the first build. survive/docs/PROCESS_REVIEW.md is the single most useful document in either repo for deciding how to work, and nothing in the skill asks for one. It is also where survive honestly records that its ARCHITECTURE_LOG was written in one go at the end and is "not yet doing its job".

STATED BIAS

13. I like this format and that is worth discounting. The cost is real: survive is roughly 920 lines of design docs against 2,400 lines of code, and oblique's set is comparable against a bot. For anything whose rules are a pipeline of obvious steps, that is pure overhead and the lighter specification skill is the right call. The threshold I would actually use: reach for ontology_spec when numbers will be tuned or when rules will be argued about. Not when the only question is what the code does.
